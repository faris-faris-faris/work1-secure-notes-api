3.3 SQL injection

Rule 1: every value is a bound parameter. src/db.js is the only module that contains SQL, which makes the rule reviewable in one file:

const user = db.prepare('SELECT * FROM users WHERE login = ? COLLATE NOCASE').get(login);

Rule 2: LIKE needs its own escaping. A bound parameter stops SQL syntax injection, but % and _ inside the value are still wildcards. A user searching for 100% should not receive the whole table, so the term is escaped and the statement declares the escape character:

function likePattern(term) {
  return `%${term.replace(/[\\%_]/g, (char) => `\\${char}`)}%`;
}
// ...
`(n.title LIKE ? ESCAPE '\\' OR n.body LIKE ? ESCAPE '\\')`

Rule 3: identifiers cannot be parameterised, so they are allow-listed. Sort order comes from the client but never reaches SQL text:

const SORT_CLAUSES = Object.freeze({
  newest: 'n.created_at DESC, n.id DESC',
  oldest: 'n.created_at ASC, n.id ASC',
  title:  'n.title COLLATE NOCASE ASC, n.id ASC',
});
const orderBy = SORT_CLAUSES[sort] || SORT_CLAUSES.newest;

Validation rejects anything outside the enum before the repository is called, so ?sort=id; DROP TABLE notes is a 400, not a query.

Evidence. tests/notes.test.js sends ' OR 1=1 --, ' UNION SELECT * FROM users -- and '; DROP TABLE notes; -- to the search endpoint: every one returns total=0, and a following assertion checks that the notes table still has its rows. The login endpoint refuses the tautology payload with 401. A separate test searches for % and gets exactly the one note that contains a literal percent sign.

3.4 Cross-site scripting

The database stores text verbatim and the API encodes it on output — the rule from the OWASP XSS Prevention Cheat Sheet. Encoding on input would corrupt the data (and double-encode on the next edit); encoding on output keeps the text usable by a JSON client while making it inert for an HTML one.

const HTML_ESCAPES = { '&': '&amp;', '<': '&lt;', '>': '&gt;', '"': '&quot;', "'": '&#39;', '`': '&#96;' };
export const escapeHtml = (value) => String(value).replace(/[&<>"'`]/g, (c) => HTML_ESCAPES[c]);

Every user-controlled field of a note (title, body, author login and display name) passes through escapeHtml in presentNote(); the test stores <script>, <img onerror>, <svg onload>, javascript: and <iframe> payloads and asserts that none of the raw forms appears in any response, while the database still contains the original text (checked directly against SQLite).

Defence in depth:

  • Content-Type: application/json and X-Content-Type-Options: nosniff;
  • Content-Security-Policy: default-src 'none'; frame-ancestors 'none' — even a document that rendered a payload could not execute script;
  • validation rejects control characters and caps each field (title 120, body 4000), which also blocks log-injection attempts;
  • unknown JSON fields are rejected (.strict()), so a client cannot smuggle author_id or role into a create request.

3.5 Authentication

Requirement Implementation
Never store plaintext scrypt, N=2¹⁵, r=8, p=1, 16-byte salt; parameters stored with the hash so the cost can be raised later
Constant-time check crypto.timingSafeEqual on the derived keys
Issue a token HS256 JWT: sub, iss, aud, iat, nbf, exp, jti; 15-minute TTL
Verify on every protected endpoint makeAuthMiddleware — signature, algorithm, issuer, audience, expiry, sub
Algorithm pinning algorithms: ['HS256'], which defeats alg: none and RS→HS confusion
Revocation the user is re-read from the database on every request; a deleted account's token dies immediately
No enumeration the same 401 body for unknown user and wrong password, plus a dummy scrypt run to flatten timing
Brute force 5 failures per (IP, login) per 5 minutes → 429 with Retry-After
Refresh 256-bit opaque token, SHA-256 at rest, rotated on every use; replay revokes the family

The refresh design deserves a note, because it is where most "JWT + refresh" implementations go wrong. A refresh token is not a second JWT: it is an opaque random string whose hash is stored in the database. Each use rotates it — the old row is marked rotated_at, a new row is inserted in the same family_id. If a rotated token is presented again, either the client replayed a request or the token was stolen; the server revokes the whole family, so the attacker's copy and the victim's session die together:

if (row.rotated_at) {
  repo.revokeRefreshFamily(row.family_id);
  throw unauthorized('Refresh token already used; the session was revoked.', 'token_reuse');
}

Evidence: tests/auth.test.js covers expired tokens, attacker-signed tokens, alg: none, a foreign audience, deleted users, lockout and the hash format; tests/refresh.test.js covers rotation, reuse detection and logout.

3.6 Access control (A01)

Every write is checked against the loaded row, not against the token alone:

const existing = repo.getNote(id);
if (!existing) throw notFound('Note not found.');
if (!canModifyNote(req.user, existing)) {
  throw forbidden('Only the author or an administrator may edit this note.');
}

canModifyNote is note.author_id === user.id || user.role === 'admin', and it lives in one place so a new route cannot forget it. The test suite creates a third user and asserts that editing another user's note is 403 while an admin can moderate it. A non-numeric id (1 OR 1=1) is a 404, not a database error.

3.9 Known limitations

  • The rate limiter and the session store are in-process: correct for one instance, but a multi-instance deployment needs Redis (or a shared table) so limits and revocations are global.
  • Refresh tokens are stored hashed but not bound to a device; a stolen token that is used before rotation cannot be distinguished from the real client.
  • The API has no CORS layer because no browser front end is part of this work. A real deployment needs an explicit allow-list.
  • SQLite serialises writes; that is ideal for a lab and wrong for a write-heavy production service.

The request is a single GET to / with parameters whose names are the exploit:

class.module.classLoader.resources.context.parent.pipeline.first.pattern=<JSP>
class.module.classLoader.resources.context.parent.pipeline.first.suffix=.jsp
class.module.classLoader.resources.context.parent.pipeline.first.directory=webapps/ROOT
class.module.classLoader.resources.context.parent.pipeline.first.prefix=tomcatwar
class.module.classLoader.resources.context.parent.pipeline.first.fileDateFormat=

plus three headers (c1: Runtime, c2: <%, suffix: %>//) that the log pattern expands into JSP source at write time. The path walks the container's object graph:

class → module → classLoader → resources → context → parent → pipeline → first
  Class    Module   WebappCL    WebRoot     Context    Host      Pipeline  AccessLogValve

first is Tomcat's AccessLogValve. Rewriting pattern, directory, prefix and suffix makes the next access-log entry a JSP file inside webapps/ROOT; the log content is the servlet source, so requesting the file executes it. The empty fileDateFormat removes the date stamp from the filename, which is why the shell is reachable as /tomcatwar.jsp. Tomcat buffers logged lines (128 KiB), which is why the script waits ~10 s before triggering the file.

4.4 Root cause

Spring MVC binds request parameters to a model attribute:

@RequestMapping("/")
public String hello(Person person, Model model) { ... }

Before 5.3.18, CachedIntrospectionResults exposed the JavaBeans class property to that binder. From Class the attacker reaches the JDK 9+ Module, its classLoader, Tomcat's web resources, the StandardContext, its parent StandardHost, the host pipeline and the first valve. Every step is an ordinary public getter; nothing checks whether the request should be allowed to touch container internals.

The defect is therefore a capability the binder should never have had, not a missing authorisation check in the demo application. Two preconditions narrow it: the application must bind a POJO (not @RequestParam individual fields), and it must run on Tomcat as a WAR, because resources.context.parent is the servlet container's object graph. On JDK 8 the chain is shorter and this exploit does not work; a Spring Boot executable jar usually has no configured access-log valve, so the published sink is absent (the underlying primitive is still considered general by the advisory).

Impact: arbitrary command execution as the Tomcat process user. In this container that user is root, hence uid=0(root); in a normal deployment it is the service account, which still owns the application, its database credentials and its files.

4.5 The fix

cve/Dockerfile.fixed rebuilds the same application with the Spring jars upgraded to 5.3.18, the release that makes class.* (and Class.*, *.class.*, *.Class.*) non-bindable. The base image has no jar tool, so the Dockerfile unpacks ROOT.war into webapps/ROOT and replaces WEB-INF/lib/spring-*.jar; Tomcat deploys the exploded directory.

docker compose down
docker compose -f docker-compose.fixed.yml up -d --build
docker exec spring4shell-fixed unzip -p \
  /usr/local/tomcat/webapps/ROOT/WEB-INF/lib/spring-webmvc-5.3.18.jar \
  META-INF/MANIFEST.MF | head -5

Why this is the right fix: the change is in CachedIntrospectionResults, so the class property is no longer reachable at all. That removes the primitive, instead of blocking the one published payload. The advisory's workaround for applications that cannot upgrade — an @InitBinder that calls setDisallowedFields("class.*", "Class.*", "*.class.*", "*.Class.*") — has to be repeated in every controller that binds input, which is why the framework upgrade is preferable.

What is not a fix: deleting the webshell (recreated on the next request), disabling the access log (loses auditing, keeps the primitive), blocking the literal string class.module in a WAF (trivial to vary), or running Tomcat as a non-root user (good hardening, but the webshell still executes with the application's privileges).

Figure 7 — the patched target: every check passes, including the two that a naive test would miss.

Why the verification does not check the status code. Spring 5.3.18 does not answer the malicious request with 400; it silently ignores the non-bindable properties and returns the normal page (200). A test that asserts "the exploit must return 400" would therefore fail on a correctly patched server and would tempt someone to "fix" the test instead of the server. The script checks the effects instead:

  1. no tomcatwar.jsp and no .jsp appears in the webroot;
  2. the access log still has its default pattern, checked from inside the container — i.e. the valve was not rewritten;
  3. the normal name/age binding still works, which catches a "fix" that simply broke the binder.

4.7 Defence in depth

  • Keep Spring and Tomcat patched; treat framework CVEs as dependency work, which is what the SCA job in Part 1 automates.
  • Bind to DTOs with explicit fields and use @InitBinder allow-lists (default-deny), not setAllowedFields on a few fields.
  • Run the container as an unprivileged user with a read-only webroot.
  • Put the application behind a WAF and keep it patched — the WAF buys time, it is not the fix.
  • Alert on class.module.classLoader in request logs: legitimate clients do not send it.

5. Conclusion

The two halves of the work meet in the same lesson. Part 1 shows that the protections the OWASP Top 10 asks for are implementable in a small service, and that each one is testable: a payload either authenticates or it does not, a script tag either survives to the client or it does not. Part 2 shows the other side of the same coin: a single framework feature can undo an entire application's security posture, and the only durable fix is to remove the capability, not the payload.

The most useful concrete finding is the verification trap. After the upgrade, the attack request still returns 200; only the effects changed. Verifying a fix by status code would have declared a patched server vulnerable, and — worse — a superficial "fix" (deleting the JSP, disabling the log) would have passed. Checking the object graph's behaviour, and re-testing normal functionality, distinguishes a fix from a workaround.

6. Control questions

1. Why is bcrypt (or scrypt/Argon2) preferable to SHA-256 for passwords? SHA-256 is designed to be fast: a GPU can compute billions of candidates per second, so a stolen digest is crackable at scale. bcrypt/scrypt/Argon2 are deliberately slow and salted: the salt defeats precomputed rainbow tables, the cost factor makes each guess expensive, and scrypt/Argon2 also require memory, which hurts GPU and ASIC attackers. This project uses scrypt with N=2¹⁵, r=8, p=1 — about 80 ms and 32 MiB per hash, invisible for one login, ruinous for an offline attack.

2. SAST vs DAST? SAST analyses source or bytecode without running the program: it sees every branch, runs in CI before deployment, and reports the file and line — but it cannot see runtime configuration and produces false positives. DAST attacks a running application from outside: it finds real, reachable issues (including configuration and authentication problems) but only on the paths it crawls, and it cannot say where in the code the defect is. They complement each other; this work uses SAST in CI, and the companion DAST work uses ZAP.

3. How does a JWT work? A JWT is base64url(header).base64url(payload).base64url(signature). The header names the algorithm, the payload carries claims (sub, iss, aud, exp, iat, jti), and the signature is an HMAC (HS256) or a public-key signature (RS256) over the first two parts. The server verifies the signature with its secret (or public key), then checks the claims — issuer, audience, expiry. The token is signed, not encrypted: anyone can read the payload, so it must not contain secrets. In this project the server also re-reads the user on every request, so deleting an account invalidates its token immediately.

4. What risks come from not auditing third-party dependencies? A project inherits every vulnerability of its dependency tree, including transitive packages nobody reviewed. Known CVEs are public and tooling makes them cheap to exploit (Spring4Shell is a single request). Without SCA you learn about the problem from an incident, not from CI. Auditing also exposes abandoned packages, licence conflicts and supply-chain risk (typosquatting, compromised maintainer accounts). npm audit in CI and OSV locally are the minimum.

5. What do Docker and Vulhub add for studying security? Isolation (a deliberately vulnerable service runs on a private network, not on the host), reproducibility (image + compose file pin the exact versions), speed (a container is destroyed and recreated in seconds, so an RCE can be repeated and the fix tested immediately), and safety (no vulnerable software installed on the workstation). Vulhub adds a curated, documented set of environments with the vulnerable versions and exploitation notes, which removes the setup work and leaves the analysis.

6. Vulnerability vs exploit — what was reproduced here? The vulnerability is the weakness (the binder exposing class.module…); the exploit is the concrete sequence that abuses it (the parameter names, the headers that build the JSP, the request to the generated file). In this work the vulnerability is CVE-2022-22965 in Spring 5.3.17; the exploit is the HTTP request and webshell produced by exploit.ps1. Reproducing the exploit proves the vulnerability is reachable in this configuration.

7. Why is regression testing critical after a fix? A patch changes behaviour by definition, and security patches often touch shared code. Without a regression check you cannot distinguish "the attack is blocked" from "the feature is broken". Here the fix could easily have been implemented by disabling model binding or the access log, which would block the exploit and break the application. verify-fix.ps1 therefore also asserts that /?name=Bob&age=25 still renders correctly.

8. Why does CVE knowledge matter for a pentester or a SOC analyst? For a pentester, a CVE gives a known-reachable primitive with public proof and a precise version range — the fastest path from "this looks like Spring" to "this is exploitable". For a SOC analyst, the same knowledge drives detection: the request signature (class.module.classLoader), the post-exploitation artefact (a new .jsp in the webroot) and the upgrade timeline. Both roles need to reproduce and verify, otherwise they are repeating rumours.
